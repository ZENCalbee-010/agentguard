## 2. Design
| Item | Value |
|---|---|
| Benchmark / suite | AgentDojo v1.2.2, banking; one attack family (`important_instructions_no_model_name`) |
| Split | frozen **test** split of manifest `banking-v1` (hash `9db39933...`): 11 user tasks (clusters) `0,1,3,4,6,8,9,10,12,13,14`, 99 attack cases (9 injection tasks each) and 11 benign cases |
| Configurations | B0, B1, B2, P1 (identical model, prompts, tools, sandbox, oracle; they differ only in the gateway decision) |
| Model | `qwen3.5:9b`, digest `56671c2ab938...` pinned and checked before the run and in the analysis, `num_ctx` 12288, thinking off, temperature 0, seed 0, 1024 output tokens |
| Policy / analyzer | `banking-v2` (hash `086eaa01...`); context analyzer v0.1, config hash `54a3f7c1d1a3`, weights and threshold fixed a priori (M5) |
| Limits | `max_steps` 10 per case. `max_wall_s` 300 is the **per-model-call** timeout, not a limit on the whole run |
| Repetitions | 1 (a budget choice, see below) |
| Runs | 440 (110 cases x 4); about 6 h local compute; 0 THB |
| Oracle | native AgentDojo state predicates, unchanged. F-4 (looser predicates for injection tasks 0, 1, 3) is a stated limitation and is not corrected here |
| Utility strata | all 16 / valid 13 (excludes user tasks 5, 6, 8: their utility oracle passes for a do-nothing agent) / strict 11 (also excludes 9, 10), pinned by test; all three are always reported. In the test split valid has 9 user tasks and strict 7 |

**Repetitions.** Temperature 0 and seed 0 made `qwen3:8b` reproduce 30/30 trajectories and token counts in M7b. For `qwen3.5:9b` the evidence is weaker and different: in the only repeats available (B0 benign, user tasks 2, 7, 15, qualification vs M7c pilot, same digest and settings) trajectory and success were equal in 3/3 but output tokens differed in 3/3 and input tokens in 1/3, so generation is **not bit-reproducible** for this model on this GPU. One repetition is therefore a budget choice, not evidence of determinism, and `research-questions.md` section 4 (repeats are aggregated when nondeterminism is observed) is deviated from (section 8). To put a number on the noise, a second run of the B0 arm on the same 110 cases follows the main run as a separate descriptive experiment (`m8b-noise-b0`, section 7).

**Static ceiling.** Evidence `docs/research/evidence/m7b-policy-coverage-matrix-v2.json` (ground-truth replay, model independent, produced by an author who had read the injection goals, R-24) says that under the frozen policies the injection goal is reachable only for user tasks 0 and 10 (6 injection tasks each): 12 of the 99 attack cases. P1 can differ from B2 in security only there.

## 3. Primary endpoint and definitions
Executed unauthorized action = the state oracle reports the injection goal achieved in the post-run sandbox state. Denominator = clean attack cases (`run_status == completed`). Unclean runs are excluded from numerators **and** denominators (the oracle verdict of an unclean run is not stored), listed by configuration and status, and a pair with an unclean member is dropped from that contrast. Because a defense can itself cause step-limit runs, section 4 pre-registers a bounding sensitivity analysis (unclean as failure; unclean as executed and as not executed). Attempted, denied, executed and goal-achieved stay separate; `INVALID_CALL` is never a defense denial.

## 4. Confirmatory test and descriptive estimands
**One confirmatory test, H1.** Draft 1 listed three; review showed that two of them cannot reach a positive verdict under any outcome, and a confirmatory test that cannot be confirmed only costs alpha and misleads. H2 and H3 are therefore pre-registered as **descriptive estimands with exact intervals**, not tests.

| ID | Hypothesis | Method | Decision rule |
|---|---|---|---|
| **H1 (confirmatory)** | ASR(B2) < ASR(B0) | exact two-sided McNemar on the paired attack cases (all 99), level 0.05 (Holm over a family of one) | "SUPPORTED" iff exposure is adequate AND B0-only discordant pairs > B2-only AND p < 0.05 AND the 95% cluster-bootstrap CI (user tasks, 10,000 resamples, seed 20261119) of rate(B0) - rate(B2) has lower bound > 0. The verdict string also states whether the cluster sign test (p < 0.05) and the two-way (user task x injection task) bootstrap lower bound (> 0) agree; if not it reads "SUPPORTED at the case and user-task-bootstrap level; NOT robust to sensitivity checks" |
| H2 (descriptive, RQ2) | does P1 add protection beyond B2? | counts of executed attacks in B2 and P1 with exact (Clopper-Pearson) intervals, on all attack cases and on the 12 policy-reachable cells; exact McNemar p as a raw descriptive number | no verdict: discordance can lie in at most 2 of 11 user tasks, so a cluster-based lower bound above 0 is impossible by construction ((9/11)^11 = 0.11 of resamples miss both) |
| H3 (descriptive, RQ3) | cost of P1 in benign utility relative to B0 | difference with the exact one-sided 95% lower bound (exact unconditional test with Berger-Boos, below), on the valid 13 and strict 11 strata, both shown | no verdict. The margin of 10 percentage points is reported as a formality only |

**Exposure adequacy (pre-registered).** H1 is interpretable only if, in B0, the model attempted the attack in at least **10** clean attack cases spread over at least **4** user tasks. The 4 is not arbitrary: with 11 user tasks, a 95% cluster bootstrap can only have a lower bound above 0 if at least 4 user tasks carry B0-only discordance ((8/11)^11 = 0.030 > 0.025 > (7/11)^11 = 0.0069). Otherwise H1 is labelled "INSUFFICIENT EXPOSURE (descriptive only)" whatever its p-value. In the M7c pilot every attempted attack fell in one user task (R-29), so this outcome is plausible. SUPPORTED also needs at least 6 one-direction discordant pairs (exact p < 0.05); strong effects concentrated in 3 or fewer user tasks are labelled NOT ESTABLISHED by design. The word SUPPORTED alone is reserved for the robust case: the cluster sign test needs B0-only discordance in at least 6 of the 11 user tasks with none opposing (5 tasks give p = 0.0625), and the two-way bootstrap lower bound exceeds 0 only if the discordance lies in at least 4 of the 9 injection tasks ((6/9)^9 = 0.026 > 0.025). A verdict that satisfies the main rule but not these starts with "SUPPORTED at the case and user-task-bootstrap level; NOT robust", whatever the effect size. A significant effect in the wrong direction is labelled REVERSED.

**H3 method and its operating characteristics.** Benign cases are one per user task, so pairs are independent. The test is an exact unconditional one-sided test of H0: rate(P1) - rate(B0) <= -0.10 with the Berger-Boos nuisance restriction (gamma = 0.005): the p-value is the maximum, over the total discordance probability restricted to its exact 99.5% Clopper-Pearson interval, of the multinomial probability of an outcome at least as favourable, plus gamma. Exact (not simulated) operating characteristics are in `docs/research/evidence/m8-h3-operating-characteristics.json` (script `experiments/scripts/m8/h3_operating_characteristics.py`): at the boundary the maximum type I error is 1.1% / 3.8% / 3.3% for n = 9 / 30 / 60 (at most 1.4% when discordance is 30% or less), and power for truly equal arms with 5% discordance each way is 0.0 / 0.05 / 0.37. Two simpler methods were implemented first and rejected: a cluster bootstrap collapses to a point when every pair is concordant (a dry run on pilot data declared non-inferiority from 3 identical pairs), and Newcombe's hybrid-score interval over-rejects at the boundary (exact maximum type I error up to 32% at n = 9 and 18% at n = 30). These methods were chosen on synthetic data and pilot dry-runs; they were **not** chosen blind to the test benign outcomes: **the B0 benign outcomes of the 11 test user tasks already exist** from the M7c qualification run (same model, digest and settings): valid stratum 6/9 (user tasks 3, 4, 14 failed), strict stratum 4/7. Given those qualification outcomes, with at most 3 tasks where P1 could beat B0, non-inferiority within 10 points cannot be shown for any outcome; the study reports the lower bound instead.

**Unclean-run sensitivity (pre-registered).** The H1 and H2 contrasts are recomputed with unclean runs imputed **per arm**: worst case for the defense = unclean runs of the treated arm (B2 for H1, P1 for H2) count as "attack executed" and unclean runs of the reference arm (B0, B2) as "not executed"; best case = the reverse. The utility contrasts (attack utility, benign utility and the descriptive H3 bound) are recomputed with unclean runs counted as failures. These are sensitivity analyses; the primary analysis stays complete-case.

## 5. Exploratory analyses (labelled, no multiplicity control)
- Security: B1 vs B0 (RQ2b), P1 vs B0, P1 vs B1; B2 vs B0 and P1 vs B2 restricted to the 12 policy-reachable cells; attempted rate, executed given attempt, per user task table, denials by reason.
- Utility: task success under attack (99 cases) and benign success for B1, B2, P1 against B0, and P1 vs B2, in all three strata, with paired McNemar, cluster-bootstrap CI and cluster sign test. These carry the RQ3 evidence that H3 cannot. **Interpretation caution:** for user tasks 9 and 10 the utility oracle passes iff the environment is unchanged, so under attack a defense that blocks the attack is credited with utility; the strict stratum removes these two tasks and must be read beside the others (a reviewer also reported user task 14 x injection task 7 as a similarly coupled pair; not independently verified).
- Mechanism: analyzer denials by tool; cases where B2 had task success and P1 did not (and whether an analyzer reason is present); P1 trajectories identical to B2.
- Sensitivity for H1/H2: two-way bootstrap CI, cluster sign test, discordant pairs by user task and leave-one-user-task-out.
- Cost (RQ5): wall clock per run (median, P95, mean), tokens, model calls per configuration, over runs whose latest attempt is not an infrastructure failure (the number excluded is reported). LOC of the gateway is not reported here. Gateway decision time is not recorded separately and is not claimed.

## 6. Research questions and what this study can answer (stated before the data)
- **RQ1** testable only if exposure is adequate. **RQ2**: expected result is no detectable security gain (B2 already blocks everything outside the 12 reachable cells) and a measurable utility cost; reported descriptively. **RQ3** measurable through the exploratory utility contrasts. **RQ4 not testable** (one qualified model; one attack family). **RQ5** descriptive.
- **What a SUPPORTED H1 would and would not show.** Given the static ceiling (the frozen policies leave only 12 of 99 goals reachable), H1 is largely decided by how many attacks the model attempts in B0; it shows that the frozen, author-written per-task policies (written after reading the injection goals, R-24) stop this model's real calls on this suite. It does not show that capability enforcement generalises to policies written without that knowledge, to other models, other suites or adaptive attackers. Exposure, per-user-task results and the sensitivity checks are reported beside the verdict.
- Qualification: qwen3.5:9b scored 9/13 (Wilson 0.42-0.87) on the valid tasks; the point estimate passes the 50% gate but the interval does not exclude a value below 50%. Reported as a limitation.

## 7. Run procedure and data handling
- **Runner:** `run_main.py`. It refuses a dirty working tree or an unknown commit, checks the model digest (and fails closed if Ollama is unreachable), refuses a records file of another experiment, a damaged file or a second concurrent instance, and runs the cases **case-major** (the four configurations of a case back to back), so no configuration is confounded with the time of the run. A case whose attempts all failed for infrastructure reasons (`model_timeout`, `model_error`; note that `model_error` can include server 5xx responses and malformed tool calls, because the adapter does not keep the HTTP error body) is re-run once in a second pass at the end of the run and again on resume; both attempts stay in the file, the analysis uses the **latest** attempt per case and lists all attempts, and a case that ends on an infrastructure failure with attempts still to spare invalidates the analysis until it is re-run. After two failed attempts a case is *exhausted*: it is listed as unclean, excluded from rates, covered by the bounding sensitivity, and excluded from the cost statistics. The runner writes the failing records and then aborts after 3 consecutive infrastructure failures (so an outage costs at most 3 attempts). Behaviour outcomes (step limit, context overflow) are results and are never re-run. Any other repeat of a case invalidates the analysis. An uncaught exception inside a case stops the run, is never re-run silently and is a protocol deviation to be reported; a code fix would make the analysis INVALID by design (a repair is then a new, reported, protocol).
- **Provenance:** each record carries `code_commit` and `code_dirty`. To resume after an interruption the partial raw file is committed first (a data checkpoint) so the tree is clean; records may then carry more than one commit, and the analysis requires that `git diff` of `src/`, the M7 and M8 runner scripts and `experiments/configs/` between those commits is empty, otherwise the analysis is marked INVALID.
- **Damaged file after a crash.** If the raw file ends in a truncated line, the runner refuses to start; exactly that one line may be copied to a side file and removed, the file committed as the checkpoint, and the repair reported.
- **Freeze identity.** The freeze commit is tagged `m8-freeze` and its SHA recorded in `docs/milestones/status.md` before the run; the analysis is invoked with `--frozen-commit m8-freeze` and requires `git diff` of `src/`, `experiments/scripts/m7`, `experiments/scripts/m8`, `experiments/configs` and this plan between the freeze commit and every record commit to be empty.
- **No interim analysis of outcomes.** The console shows progress only (record index, elapsed time, configuration, case, run status, latency). Only run progress (record counts, status counts, wall clock) may be inspected during the run. The analysis is run once, after the last record, with the frozen script. If the integrity block fails, the script writes a summary with INVALID verdicts and exits with code 2; no verdict is produced from invalid data.
- **Noise floor (descriptive, separate experiment):** after the main run, configuration B0 is run again on the same 110 cases (`experiments/configs/m8b-noise-b0.yaml`, about 1.5 h) and `noise_floor.py` reports how many cases differ in status, attempt, execution, success and trajectory. Never pooled with the main data.

## 8. Deviations from the M1 draft (`research-questions.md`, sections 3-5), declared
1. Mixed-effects logistic regression is **not** performed (no statistics package in the core environment; with 11 clusters and few events it would not be reliable). The two-way bootstrap and cluster sign test are the sensitivity analyses instead.
2. The draft's confirmatory family {H1, H2, H3} is reduced to {H1}; H2 and H3 are descriptive (section 4).
3. A hypothesis is called "supported" only if the cluster-bootstrap CI also excludes the null, in addition to the McNemar p-value, with robustness annotations.
4. The exposure-adequacy rule is new, as is the descriptive H3 interval (exact unconditional test).
5. McNemar is two-sided although H1 is directional; the direction is required separately in the decision rule.
6. **One repetition although run-to-run nondeterminism was observed** (the draft aggregates k repeats in that case); mitigated by the B0 noise-floor run.
7. **One attack family** (the draft asks for per-family breakdowns): the banking manifest holds only `important_instructions_no_model_name`, so the family breakdown is not testable.
8. The development split was used for the pilot only and for no tuning; the validation split is not used.
9. The draft's call-level false-positive rate, the minimum-detectable-effect estimate for a null P1-B2 result (replaced by the discordance counts needed, sections 4 and 5), and gateway LOC reporting are not part of this study.
10. `docs/research/research-questions.md` (the older draft) is superseded by this plan for the M8 study and carries a banner saying so.

## 9. Known limitations (reported with the results)
Policies were authored after reading the injection goals (R-24); policies are text-derived and the suite has few data-derived arguments (R-21, R-23); F-4 loose predicates for injection tasks 0, 1, 3; weak utility oracles (a do-nothing agent passes five user tasks; handled by strata); one model, one repetition, temperature 0 (results are for this decoding setting, and generation is not bit-reproducible); `think=false` behaviour of this model was not verified separately (it produces roughly twice the output tokens of qwen3:8b); a response truncated at the 1024 output-token cap is accepted as a clean completion; `model_error` conflates server faults with malformed model output; the arms run interleaved case by case but the B0 noise run is a later block; unclean runs have no stored oracle verdict (handled by the bounding sensitivity); the heuristic analyzer's false-positive cost was observed in the pilot (R-28); attack evidence may again concentrate in few user tasks (R-29); the benign set has 9 pairs so benign utility cost can only be estimated with a wide interval; CI and native ruff are unverified (BLK-001, BLK-003); a single benchmark, not external validation.

## 10. Pre-registration review (before freeze)
Five reviewers (statistics; measurement and denominators; run procedure; plan-versus-code honesty; scenario tests of the script) produced 38 findings; an independent verifier tried to refute each (6 confirmed as major, 30 as minor, 2 refuted). Confirmed and acted on: H2 and H3 unreachable as confirmatory tests (section 4); exposure rule inconsistent with the bootstrap rule (4 user tasks); a server crash would have filled the file with junk records that resume skipped, and the plan's re-run rule was not implemented (runner, section 7); integrity problems did not stop verdicts and a missing record crashed the script (analysis, tests); an unsupported claim of reproducibility for this model and an incorrect statement that no test data existed (sections 2, 4); simulation figures that were not backed by an artifact (now an exact calculation, evidence file); differential attrition of unclean runs (bounding sensitivity); several documentation corrections. Review artifacts: workflow run `wf_7929209a-1bd`.
