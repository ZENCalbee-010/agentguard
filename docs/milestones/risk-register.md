# Risk Register

Likelihood/Impact: L/M/H. Status: Open / Mitigating / Closed. Updated: 2026-11-18 (M0/M1).

| ID | Risk | L | I | Mitigation | Status |
|---|---|---|---|---|---|
| R-01 | Local models that fit 8 GiB VRAM produce unreliable tool calls → low benign utility; the defense would look "effective" only because the agent fails | H | H | M4 qualification gate on benign tasks; report utility alongside ASR; never count model failure as a defense success (oracle distinguishes) | Open |
| R-02 | Base attack success rate on B0 is low (small models often ignore injections) → no measurable room for defenses; RQ1/RQ2 underpowered | M | H | Pilot (M7) measures B0 ASR first; report Attempted vs Executed separately; consider API model for external validation (needs approval) | Open |
| R-03 | AgentDojo cannot drive Ollama models natively, or version requires a different Python | M | H | M2: Python OK (3.13 works, `>=3.10`); native semantics verified without LLM. Ollama-driven native run verified on 1 case (`m2-llm-smoke.json`); remaining risk is tool-call reliability across suites/models (R-01); fall back to documented adapter or isolated custom suite with stated limitations | Mitigating |
| R-04 | Novelty: combining detector + capability policy is very likely **not** novel (e.g. LlamaFirewall, Progent, CaMeL, Task Shield address overlapping ideas) | H | M | Related-work matrix; frame contribution as controlled factorial evaluation (B0/B1/B2/P1) + intent-bound scoping, not as a new mechanism, unless the review shows a real gap | Open |
| R-05 | P1 ≈ B2 (detector adds nothing once permissions are enforced) | M | M | Pre-registered as a valid null result (RQ2); report honestly | Accepted |
| R-06 | Policy for B2/P1 is hand-written per task → could leak ground-truth knowledge of the attack ("oracle policy") and overstate protection | M | H | Policies derived only from the **user task text + tool schemas**, written before viewing injection goals, frozen and hashed; documented in requirements REQ-POL-4 | Open |
| R-07 | Oracle coupled to the defense (e.g. counting a DENY as "attack blocked" without checking state) | L | H | Oracle reads only sandbox state diffs; independent of gateway code (SEC-010, REQ-ORC-*) | Open |
| R-08 | Context-window truncation (Ollama default 4096) silently drops injected content or tool schemas | M | H | Explicit `num_ctx`; log prompt token counts; fail the run if prompt tokens ≥ num_ctx | Open |
| R-09 | Local inference throughput too low for full factorial (cases × 4 configs × models × repeats) | M | M | Pilot timing → size main study; subset of suites | Open |
| R-10 | Self-review is not independent | H | M | Evidence-based review reports; recommend separate review session; never claimed as external audit | Accepted |
| R-11 | BLK-001 (ruff file access) masks lint regressions locally | L | L | stdin wrapper + CI native ruff | Mitigating |
| R-12 | CI unverified (no remote, push needs approval) | H | L | Request approval to push when a milestone is ready | Open |
| R-13 | Windows vs POSIX path semantics in resource normalization (SEC-011) | M | M | Normalize virtual sandbox paths with `PurePosixPath` independent of host OS; dedicated tests | Open |
| R-14 | Statistical dependence: repeated runs and templated attacks treated as independent → inflated significance | M | H | Unit of analysis = (task, injection) case; paired McNemar / cluster bootstrap by task; repeats aggregated per case | Open |
| R-15 | Paid API budget (3,000 THB) exceeded | L | M | No paid calls without approval; pilot measures tokens/case; hard cap in config | Open |
| R-16 | Benchmark oracle defects (F-1..F-5 in benchmark-compatibility.md): trace-based oracles count proposed calls; 3 banking oracles looser than stated; 8 workspace oracles lack positive controls | H | H | Adapted executed-trace oracle (needs approval); exclude unvalidated tasks from primary set; report native and AgentGuard metrics separately; sensitivity analysis | Open |
| R-17 | Unreliable network slows/aborts model downloads | M | L | Resume pulls; smaller model fallback | Open |
| R-18 | In-process design: code in the same Python process could bypass the gateway API (S-1 in M3-report) | L | M | Threat model A1; the model never runs Python; revisit if generated code is executed | Accepted |
| R-19 | Hung analyzer threads exhaust the 2-worker pool (S-2); later B1/P1 calls time out | L | L | Fails closed; M5 analyzer is pure/fast | Accepted |
| R-20 | M3 mock tools differ from AgentDojo tools; adapter semantics unverified | M | M | Banking adapter verified against AgentDojo ground truth and native oracle (B0 144/144 parity). Other suites not adapted | Mitigating (banking only) |
| R-21 | Policies derived only from task text (D-007) cannot pin arguments that come from data (e.g. the recipient of a bill read from a file); such tools need `any_value`, so B2 cannot stop recipient redirection there. The B2-vs-P1 comparison will be largely decided by how many tasks are data-derived | H | H | Mark each task `data_derived`; report results stratified by it; do not tighten policies using attack knowledge (R-06) | Open |
| R-22 | Local-model qualification depends on generation settings (thinking on/off, `max_output_tokens`, `num_ctx`); results are valid only for the recorded parameters | M | M | All parameters are stored in every record; settings frozen before the pilot | Open |
| R-23 | In banking only 3 of 16 user tasks have a data-derived payee (2 with a free amount, 1 with the amount pinned), so the frozen policies already stop most injection goals at B2; the detector's incremental value (RQ2) may be small or null on this suite | M | M | Report it as a possible null result; extend to suites with more data-derived arguments; stratify by data-derived | Open |
| R-24 | Policy author had read injection goals before writing policies (M2) | H | M | Disclosed; policies frozen by hash before analysis; no change in response to results; report as a limitation | Accepted |

| R-25 | Utility oracles of banking user tasks 5, 6, 8, 9, 10 pass without any action (F-6), so utility cannot measure task completion there | H | H | Report utility on discriminating tasks separately; decide exclusion/adaptation (needs approval) | Open |
| R-26 | Attack exposure depends on the model's own flow (38% attempted in B0 pilot; 0/9 for user task 15), so many attack cases carry no information | H | M | Report attempted separately; stratify by exposure; consider stronger/other models | Open |
| R-27 | qwen3:8b (5/13) and llama3.1:8b (2/13) are not adequately qualified on the meaningful AgentDojo banking tasks; qwen3.5:9b (9/13, interval 0.42-0.87) passes by point estimate only | H | M | Use qwen3.5:9b; confirm threshold (E); try a second model for RQ4; optional approved paid validation | Mitigating |
| R-28 | The analyzer denies legitimate protected calls when instruction-like text is in context: measured in P1 (9 denials, all the legitimate rent update; 8 of 8 comparable cases lost task success) with no security gain over B2 | H | M | Report as a finding; any change is a new analyzer version tuned on the development split only | Open |
| R-29 | In the qwen3.5 pilot all executed attacks fall in one user task (cluster), so attack-side inference has effectively one cluster | H | H | Resolved on test split: M8 B0 attempts span 6/11 user tasks (32 attempts), passing exposure adequacy and cluster sign test ($p = 0.03125$) | Closed (test split) |
| R-30 | RQ4 cannot be tested: of four local models, only qwen3.5:9b qualifies (qwen3:8b 5/13, llama3.1:8b 2/13, gemma4:e4b 5/13 in both thinking settings, mostly by not acting) | H | H | Report RQ4 as not testable; options: try lfm2.5 or other models, or approved paid API validation (G) | Open |
| R-31 | qwen3.5:9b generation is not bit-reproducible at temperature 0 / seed 0 (output tokens differ in 3/3 repeated B0 cases on Windows RX 7600), so some B0-vs-defense discordance may be run-to-run noise | M | M | Mitigated on M8 hardware: M8b noise floor on Apple M2 Pro Metal showed 0/110 differences across status, attempt, execution, task success, trajectory, and tokens (exact 95% CI `[0.000, 0.033]`) | Mitigated (M8b verified) |
| R-32 | Unclean runs (e.g. step limit caused by denial loops) have no stored oracle verdict, so a defense can hide part of its own cost by creating unclean runs | M | M | Observed in M8 (0 B0, 5 B2, 6 B1/P1 `step_limit`); bounded via worst-case/best-case per-arm sensitivity (H1 remains SUPPORTED even in worst case) | Mitigating |
| R-33 | Execution platform migrated between M7d (Windows 11 / RX 7600 / Python 3.13.14) and M8/M8b (macOS Apple M2 Pro / Metal / Python 3.14.6) | M | M | Exact model digest (`56671c2ab938`), AgentDojo freeze (`0.1.35`), and frozen code verified; all 4 M8 arms interleaved on the same machine; documented in D-021 and `m8-main-report.md` | Accepted |
